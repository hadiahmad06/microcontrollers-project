## Verified claims

Spec and range proofs (proposal sections 2 and 3), checked independently:
- Sums: 15 * -2048 = -30720, 15 * 2047 = 30705; every partial sum of at most 15 samples lies in that interval, so int16 holds.
- |mean| <= max|x| so mean is in [-2048, 2047]; d = x - mean in [-4095, 4095]; d*d <= 16,769,025 needs int32 (cast before the multiply is present; the asm uses `mul.ss w2,w2,w8`, a 16x16 to 32 multiply).
- Worst-case sum((x - mean)^2): enumerated all 16 vertices (k lows, 15-k highs, truncated mean) = 62,604,360 at k=7 and k=8, as claimed. A 3000-start coordinate hill-climb over the whole box (interior values included) found nothing larger. 62,604,360 >> 11 = 30,568; clamp threshold 32768 * 2048 = 67,108,864 is above it. The loose bound 15 * 4095^2 = 251,535,375 < 2^31.
- 34953 = ceil(2^19/15) (2^19/15 = 34952.53); excess 34953*15 - 524288 = 7; error s*7/(15*2^19) < 1/15 iff |s| < 2^19/7 = 74,898. Max |s|*34953 = 1,073,756,160 < 2^31. Exhaustive checks in div15_check.c and compare.py both run in `make test`. 61,426 = 30720 + 30705 + 1 is the right count.
- `make test` output reproduced: PASS 10062/10062, DIV15 PASS.

16-bit int hazards in features.c (every expression):
- line 30 `sum + x[...]`: int16 + int16 promotes to 16-bit int; safe by the range proof (30705 / -30720).
- line 32 `sum / 15`: signed 16-bit divide, `repeat #__TARGET_DIVIDE_CYCLES; div.sw`, truncating like C99 and the Python `c_div_trunc`; no `__divsi3`. No INT_MIN/-1 case.
- line 36 `x - mean`: result in [-4095, 4095], safe in 16-bit int.
- lines 37-38: cast to int32_t before the multiply; dd >= 0 so `(uint32_t)dd` has no sign surprise; acc < 2^26.
- line 41 `acc > 32767u`: the 16-bit unsigned constant is promoted to uint32; asm does a correct sub/subb 32-bit compare.
- Indices: `first + j` max 149, `FEAT_SEG_LEN * s` max 135, `20*a + 2*s` max 58, `idx + 1` max 59, all int16-safe. The asm steps the pointer by 6 bytes per row, no 32-bit address arithmetic. int16_t loop indices are fine for these bounds.
- The only way to break the proof is violating contract C1 (out-of-range samples), which silently wraps the int16 sum (Question 1).

XC16 output (xc16-gcc 2.10 in a temp dir, `-O1` and `-O2`, `-Wall -Wextra -Wconversion`, plus `-pedantic`): zero warnings for features.c.
- No library calls (`__divsi3`, `__mulsi3`, `__udivsi3` all absent); at -O1 the only call is `rcall _segment_features`. `.text` 0x98 address units = 76 instructions = 228 bytes, matching the proposal. 32-bit ops are the expected `mul.ss`, `add/addc`, `lsr/sl/ior`, `sub/subb`.
- Cycle estimate (hand count from asm; no simulator was available): sum loop about 6 cycles/iter x 15 = 90; deviation loop about 9 cycles/iter x 15 = 135; divide about 20; shift/saturate/store/prologue about 30. About 275 per segment x 30 = about 8.3k, so about 8.5k cycles per window with call overhead (about 2.1 ms at 4 MIPS, 1.1 ms at 8 MIPS, 0.5 ms at 16 MIPS). Negligible against a 1.5 s window. Estimate only; on-target measurement (ticket 3.10) still needed.

Python reference:
- `c_div_trunc` applies `//` only to `abs()` values; `shr_nonneg` raises on negatives; `mean_mulshift` is non-negative only. No `/`, no float, no `%`, no `>>` on negatives. `extract` runs on Python ints (`wins[i].tolist()`), so numpy int16 wraparound cannot mask a mismatch, and it re-asserts int16 range of sum, mean, d and the uint32 limit of acc.
- gen_vectors.py: `-alt - 1`, `np.full(..., dtype=int16)` do not overflow in the used ranges; generated data is clipped to [-2048, 2047]. The built vectors.bin has min -2048 and max 2047, so C1 is respected. Windows are written `<i2`, contiguous (N,150,3), sample-major, matching host_runner's `win[150][3]` read.

Does the comparison cover all 60 features of every window? Yes, and it is not vacuous:
- compare.py reads windows as (N,150,3) and features as (N,60), both `<i2`, asserts equal N, and compares whole 60-element lists exactly (`ref != got`). I checked the built files: 10062 windows in, 10062 feature vectors out.
- A wrong-size file would make `reshape` raise rather than pass. Endianness: `<i2` in Python vs native in C; identical on little-endian hosts (the PIC24 is little-endian too); a big-endian host would mismatch loudly, not pass.
- Mutation tests (temp copy of features.c, harness rerun): shift 10 instead of 11 FAIL (10040/10062 windows differ); `d*d` truncated to int16 (the T2 bug, emulated) FAIL (10040/10062); floor instead of truncate FAIL (10060/10062); saturation threshold raised PASS (expected, branch unreachable, see finding).
- Limits: the host runs 32-bit int, so the true 16-bit behaviour is evidenced only by the asm review above and by the mandatory on-target run (gate G3). Python and C come from one author and spec, so vectors prove equivalence, not that the spec is the right one.

## Proposal quality (C3_features.md)

- Decision 1 (truncate toward zero): sound, native C, one `div.sw`, Python emulation is explicit and tested. Agree.
- Decision 2 (plain `/15`, mul-shift as fallback): sound; proof checked. Agree.
- Decision 3 (energy about the truncated integer mean): sound and orthogonal to the mean feature. But PLAN section 1 C3 and INITIAL_OVERVIEW say "Energy = sum x^2" / "mean and energy"; option (b) is a real contract change, so lock it knowingly. Note also that with a truncated mean it is the sum of squared deviations (variance-like plus 15*(mean error)^2), not exactly a variance; state this in the final contract.
- Decision 4 (shift 11): I do not think it is justified for realistic motions; recommend a smaller shift (about 8, final value from recorded data) with saturation live. The argument "saturation never fires" optimises for a theoretical worst case no real gesture reaches. 1 count is about 1.95 mg (4 g / 2048). Energy at shift 11 for a segment with roughly constant deviation `dev` counts: dev 5 -> 0, 10 -> 0, 20 -> 2, 50 -> 18, 100 -> 73, 256 (about 0.5 g) -> 480, 512 (about 1 g) -> 1920. Anything with RMS deviation under about 12 counts (about 23 mg: sensor noise, gentle motion) rounds to 0, and even a 1 g swing uses only about 1920 of the 32767 range. At shift 8: dev 20 -> 23, 100 -> 585, 512 -> 15360, saturating at RMS dev about 748 counts (about 1.5 g). A smaller shift costs nothing, but then the saturation branch becomes reachable and needs vectors (finding 2).
- Decision 5 (axis-major `20*a + 2*s + k`): fine; just keep training and model index mapping identical. Agree.
- Decision 6 (rely on C1): reasonable; name who guarantees it and consider a debug-only assert (violation silently wraps).
- Missing for C1/C4: (1) Feature normalisation is not defined, yet PLAN section 1 C3 lists it ("Normalization (subtract mean, scale) in fixed point"). Means span about +/-2048, energies span 0..30568 and are heavily skewed; an int8 MLP input and the k-NN learn mode need a per-feature scale or a compressing transform (e.g. integer sqrt or log-like energy compression) so distances are not dominated by a few large energies. The proposal only mentions it under open questions; make it an explicit decision or follow-up contract with an owner. (2) Mean features depend on device orientation (gravity); training data needs varied orientations. (3) Sampling-rate coupling (T4): 15-sample segments are 0.15 s only at 100 Hz; window length and ODR should be stated as part of C3.
- The T2 caveat and open questions are honest and accurate.
