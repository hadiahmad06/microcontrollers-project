# S1-1R review: C1 capture buffer and C6a sensor I/O proposals

Reviewer: review-3 (fact-checker, no code written). Date: 2026-11-14.
Reviewed: `docs/agent/hadi/proposals/C1_capture_buffer.md`, `docs/agent/hadi/proposals/C6a_sensor_io.md` (from `main`, d07045c). Cross-read: C3_features.md, PLAN.md.

## Verdict: APPROVE WITH NITS

No factual error blocks the proposals. All four reported contradictions resolve. Three medium items (watermark edge stall, ring sizing, JTAGEN default) and a few low items need a sentence or two in the proposals before the contract is locked.

## Logic review
**Stream mode + software ring gives exactly 150 samples with 15 pre-trigger and no overflow: yes, with the conditions in the findings.** The window is counted by sample index (15 from ring + trigger + 134 more = 150), independent of ISR latency. Drain budget: WTM fires at 16 unread; the FIFO holds 32, so the first overwrite is 16 ODR ticks later (160 ms; the proposal's figure is conservative by one sample). A 16-sample burst is 8.93 ms at 100 kHz, 2.23 ms at 400 kHz; the FSS read adds about 0.4 ms at 100 kHz. Duty is about 5-6% at 100 kHz, so no overflow unless interrupts stay masked for more than about 150 ms. The 2 ms WS2812 mask is harmless to this deadline. OVRN at drain start inside an open window correctly drops the window.

**12-bit `>>4` vs C3's input range [-2048, 2047]: consistent.** HR word is left-justified 12-bit with the low 4 bits zero, raw range [-32768, +32752], so arithmetic `>>4` gives exactly [-2048, 2047] with no loss. C3's range proofs (15 x 2048^2 = 6.3e7, int16 sums <= 30720) hold only if the driver guarantees that range, which `>>4` of an int16 does. Sample-major `int16_t buf[150][3]` matches C3.
