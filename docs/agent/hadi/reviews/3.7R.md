## Findings
1. **Low (test gap)** firmware/test/gesture: `gesture_set_trigger` has no scenario and no OP (nothing in test_gesture.c
   or run_tests.py calls it). Fix: add OP_TRIG; check threshold 0 gives no windows, a high value suppresses the
   gesture, a low value restores it, and a call before init is ignored.
2. **Low (test gap)** run_tests.py: stream switched off while a WINDOW is pending (after classify, before start) and
   while a WINDOW/HELLO is in flight is specified (G2, C2 section 8) but untested. Fix: scenario with
   `STREAM 0` immediately after classify and again mid-frame (use rate=3 as in send_lock); expect a complete CRC-clean
   frame, no further HELLO, and a following gesture captured (proves release).
3. **Low** gesture.c:318-322 (bring-up): the `OVR n` text has priority over full chunks already queued, so on the wire
   it precedes up to 32 rows that were captured before the gap. The PC learns only "a gap near here, +/- 32 rows".
   chk_bring checks only the text. Fix (cheap): take the OVR line only when `bu_full == 0`, or say in the header that
   the position is approximate. Also add a check that the gap rows are consistent.
4. **Low** gesture.c:216, 73: in bring-up, toggling the stream off then on leaves `bu_fill` partial, so one chunk
   splices rows from two periods with no marker. Fix: on switch-on (`gesture_stream_raw`) reset `bu_fill` when the
   current buffer is not in flight.
5. **Low (timing, not measured)** gesture.c:398-439: worst-case drain is 64 samples (about 10 ms of I2C at 400 kHz)
   plus trigger/capture work, close to the 128 B ring's 11 ms of cover, and the pump comes only after it. Underrun just
   leaves a gap between bytes inside a frame. Fix if the PC decoder has an inter-byte timeout: pump once before the
   drain when `F_MORE` is set, or keep the decoder timeout > classify time. Classify time (API_glue finding 8: must be
   < 320 ms at 100 Hz) has no on-target number yet; put it on the HAL ticket.
6. **Info** gesture.c:420-427: a click latched into `win_events` only when a window is already CAPTURING/READY at the
   time the flag is taken; a click taken in the same poll before the window opens still sets `events` but not the
   per-window latch (drain runs first, so only the rare click-before-trigger order is affected). Accept.
