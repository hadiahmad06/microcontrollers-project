### 2. CRC

- Python snippet (/tmp scratchpad): poly 0x1021, init 0xFFFF, refin false, refout false, xorout 0 gives `0x29b1` for `b"123456789"`. Confirmed independently.
- The same parameter set is the catalogue entry CRC-16/IBM-3740 (aliases CRC-16/CCITT-FALSE and CRC-16/AUTOSAR), check 0x29B1 (recalled from memory by me as well; the page was not fetched). Nearby sets differ as expected: init 0 gives 0x31C3 (XMODEM), init 0x1D0F gives 0xE5CC (AUG-CCITT).

- "Catches all odd-bit errors": 0x1021 has 4 terms so it is divisible by (x+1); correct. Exhaustively checked on the 18 B HELLO: all 1-, 2- and 3-bit error patterns in bytes 2..17 are detected (0 undetected of 1, 2 and 3 bit combinations).

### 4. Decoder

- A valid frame cannot be lost by the algorithm itself: after any failure the decoder drops one byte and rescans the retained buffer, so a real frame behind a false candidate is found once the false candidate fails. The only theoretical loss is a false candidate whose CRC happens to pass (about 2^-16 per candidate), which would consume bytes of the real frame. The wording "can never swallow a good frame" (decision 4, :23) should read "except by a CRC collision".
- A real frame is also lost if a bit error hits its sync bytes (the CRC does not cover them): expected, visible as a SEQ gap, not a bug.
- A corrupt frame cannot be accepted unless CRC collides (about 2^-16 per candidate); 1-, 2- and 3-bit errors are all caught on HELLO as shown.
- Problems: F-03 (the delay bound is wrong, up to 114 s idle), F-04 (reserved types accept any LEN up to 1024 and are untested; the stated rule does not match the code).
