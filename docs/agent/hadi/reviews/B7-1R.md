# B7-1R: review of PR #6 (bench bring-up: APP_MODE 0-4, WS2812 driver, HC-06 helper)

Reviewer: review-31, working for hadi. Scope: `firmware/app/main.c`, `firmware/hal/pic24/ws2812_*`, `config_bits.c`,
`models/gesture_model.h`, AI_USAGE/markers, plus the code those call (`port_pic24.c`, `display.c`, `lis3dh.c`, Makefile).
Method: read the diff, assembled/compiled ws2812_send.s and ws2812_pic24.c with XC16 v2.10 and read the disassembly.
Linking is broken in this sandbox (the restricted-licence xc16 cannot resolve device SFR symbols even for a trivial
`LATBbits` program), so nothing was run; the cycle counts below come from the disassembly plus the PIC24 timing rules.

## Verdict: MERGE AFTER FIXES

No blocker for modes 1/3 (already bench-verified). One real defect hits modes 0 and 4 (F1); the rest are minor.

## Findings (most severe first)

### F1 (major) `port_take_click_flag()` re-enables INT1 on floating RB12; the "INT1 off" override in main() is undone in modes 0 and 4
- `firmware/app/main.c:402` clears `IEC1bits.INT1IE`, but `firmware/hal/pic24/port_pic24.c:155-158` (`port_take_click_flag`) does
  `INT1IE = 0; ...; INT1IE = 1;` unconditionally, and `firmware/src/gesture.c:423` calls it on every `gesture_poll()`.
  So after the first `gesture_poll()` in mode 0 and mode 4, INT1 (RB12, no INT2 wired, PPS-mapped, TRISB12 = input, no pull-up) is enabled again at priority 4.
- Scenario: RB12 floats on the breadboard (HC-06 and the WS2812 data line are right next to it). Noise edges set `s_click_flag`; each one makes
  `gesture_poll` do an extra I2C read of CLICK_SRC (and clears a real latched click); a chattering pin can also cost ISR time. TODO T-1 and the comment
  at main.c:402 both assume "no click events arrive", which is false after the first poll. Modes 2/3 are unaffected (they never call `port_take_click_flag`).
- Fix: do T-1 (drop the INT1 mapping/ISR/enable in `port_pic24_init`), or minimum: make `port_take_click_flag` restore the previous IE state instead of forcing 1,
  or guard the INT1 enable/ISR with a `PORT_NO_INT2` macro that main.c's build defines. Do not rely on the one-shot disable in main().

### F2 (minor) Brightness values are scaled by `DISPLAY_CAP`, not capped; mode 3 rim, calibration marker and tap flash are at 0..1 of 255
- `firmware/src/display.c:24-26`: `cap_channel(c) = (c*32 + 127)/255`. main.c passes 0..32 as if it were the cap, so `32 -> 4`, `10 -> 1`, `8 -> 1`, `4 -> 1`.
  Comments at main.c:75-78 say "capped to DISPLAY_CAP by display_set" (display_set does not cap; display_render scales).
- Effect in mode 3 (`level_draw`): the heat colour `hot 0..32` has only 5 output levels (0..4), so the "temperature map" gradient is 5 steps; the rim (`/3`) and the
  calibrating marker (8) are level 1; the re-zero "white flash" `fill(4,4,4)` is level 1 (the spec'd "brief white flash" is barely visible). Mode 1 colours are level 4 (visible but dim).
- Suggested fix: pass 0..255 values (e.g. multiply by 8: core up to 255, rim /3, flash 64, marker 96) and let `display_render` do the scaling and the current limit; fix the comments.
  Skip if the dim look is what the owner wants.

### F3 (minor) Reset-gap check can be satisfied by a stale pending tick (back-to-back frames only)
- `firmware/hal/pic24/ws2812_pic24.c:33-40`. A frame runs ~2.0 ms (192 B x 8 bits x 21 cycles + gaps) with IPL 7. Timer1 overflows during it set T1IF once; the ISR runs right after the IPL restore.
  `s_last_ms = board_millis()` is read after that. If the read happens before the pending ISR (or the pending tick is followed by a real overflow within microseconds), `board_millis() - s_last_ms >= 2`
  can become true after as little as tens of microseconds, not the intended >= 1 ms (WS2812 latch needs >= 300 us).
- In the unoptimised XC16 output the read is several instructions after the SR write, so the ISR almost always runs first (then the worst case is >= 1 ms). It only matters for callers that retry immediately:
  the blank frame followed by the HC-06 blue pixel frame (`main.c:405`, `main.c:381`). Modes 1/3 space frames >= 40 ms apart.
- Fix: require `< 3U` instead of `< 2U` (guarantees > 1 ms of low even in the bad case), or compare against a free-running timer value, not the lossy tick.
- Consequence of the accepted mask-the-whole-frame design (T-2, not a finding): `board_millis` loses 1-2 ticks per frame (T1IF is a single latched flag), so the clock runs ~2 ms slow per frame
  (about 5% at mode 3's 25 fps). The 40 ms frame timer and the 50 ms drain backstop stretch slightly; harmless. UART TX stalls ~1.6 ms per frame in mode 4 (4-byte HW FIFO drains in ~0.4 ms) but loses nothing.
  INT0 edges latch in IFS0 (no loss). RX is unserviced anyway; a >4-byte burst during a frame would overrun (no RX use today, relevant only once C6.1's RX ISR exists).

### F4 (minor) `make record.hex` / `bringup.hex` no longer link (documented path in hal/pic24/README.md)
- `firmware/build/Makefile` picks up `hal/pic24/*.c` by wildcard, so `ws2812_pic24.c` is now in the image, but `ws2812_send.s` is not assembled/linked: undefined `_ws2812_send_asm`.
  The Makefile also only builds `main_record.c`, so it cannot build the new `main.c` modes. (Owner currently builds in MPLAB X, so this does not block bench work.)
  Also `make check` fails on this machine at `lis3dh_hal_pic24.c:165` (`-Wsign-conversion` under clang), so the README's "host syntax check" claim does not hold with the default `cc`.
- Fix: exclude `ws2812_pic24.c` from `HAL_C` for the record image, or add a `.s` rule (`$(CC16) -mcpu=$(MCU) -c`) and add the file; mention that the Makefile does not build main.c.

### F5 (minor) Mode 3 baseline is taken immediately after a double tap while the board is still moving
- `firmware/app/main.c:493-497`, `level_feed`. `level_recal()` starts averaging 32 samples (0.32 s) right after the tap is detected; the tap itself rings for tens of ms and the user's hand is still on the board.
  The zero point is then off by the residual motion, and the blob sits off-centre until the next tap. Same at boot if the board is moving.
- Fix: discard the first ~10-20 samples after `level_recal()`, and/or restart the average if the running max-min of any axis exceeds ~50 counts (0.1 g).

### F6 (minor) RB4 is driven by two things in mode 3
- `sensor_service` (main.c:329, 336) raises/lowers RB4 around every drain; `show_frame` (main.c:66-67) also drives RB4 (toggle per frame). The header comment (main.c:23) says RB4 toggles per frame in mode 3,
  but a scope sees both interleaved (drain pulses every ~50 ms plus level changes on frame sends). Not wrong for a logic analyser in mode 2 (no frames).
- Fix: use a second pin for one of the two, or gate `show_frame`'s toggle on `APP_MODE != 3`.

### F7 (minor, course rules) `.gitignore` line without markers and without a trailing newline
- `/mplab-final-project.X/dist/` added by the AI in commit b536772 is not wrapped in `# [AI-GENERATED: Claude Code]` / `# [END AI-GENERATED]` (the adjacent `!firmware/build/` line is) and the file has no final newline.

## Checked and found correct

- ws2812_send.s cycle counts (from disassembly: bset, 4 nops, btss, bclr, 5 nops, bclr, 4 nops, sl, dec, bra): 0-bit high = 6 cycles (375 ns), low 15 (938 ns); 1-bit high = 12 cycles (750 ns), low 9 (563 ns, T1L = 9 as in C6.3); period 21 cycles = 1.3125 us. All within +-150 ns of 0.4/0.8/1.25 us. (T0H 375 ns is just under the V5 part's 380 ns max; fine for the contract's 9-cycle old-WS2812B choice.)
- The last bit of every byte gets +4 cycles (bra not taken 1, dec W1, bra taken 2, mov.b, mov = 6 vs 2): low time only, harmless. The pin ends low after the last bit; n == 0 returns immediately.
- `bset LATB,#15` assembles to `bset.b LATB+1,#7` = bit 15 of LATB (RB15, pin 26); one word, one cycle; no read-modify-write hazard with interrupts masked. `btss` skipping a 1-word `bclr` is 2 cycles as assumed.
- Calling convention: W0 = pointer, W1 = count, only W0-W3 touched (caller-saved); `mov.b [W0++],W2` with a stale high byte of W2 is fine because only bit 7 is tested and `sl` shifts the word.
- IPL: compiled as `ior #0xE0, SR` (set 7) and an and/ior restore of SR<7:5>; restore reinstates the saved level, not 0. No interrupt can fire between the read and the write at IPL 7. RB15 is digital (`AD1PCFG = 0xFFFF`) and `LATB15` is cleared before `TRISB15`.
- `board_millis` is a single 16-bit load; `uint16_t` wrap arithmetic is correct everywhere in main.c; first frame (`s_sent` false) never blocks, so the boot `while (!show_frame())` cannot hang.
- Mode 3 math with 16-bit `int`: `d` in +-4095, `d - s_filt` in +-8190, all int16-safe; position, radius and distance terms are int32 (max d2 about 25k); `hot` 0..32, `grn = 32 - hot` never underflows; sums are int32; `/ LEVEL_CAL_N` is int32. X to columns, Y to rows (`col*16 - cx`, `row*16 - cy`) with the flip macros applied before the clamp; rest centre 56 = 3.5 px; the 2x2 rest blob (distance^2 128 <= r^2 144) is lit at the rim level.
- `sensor_service`: `more` is reset by `lis3dh_drain` on each call, the loop ends on error or when the FIFO is below 16 (max 2 passes at 32 deep); I2C HAL loops are bounded; the click poll is inside the RB4 window; INT0 flag read-and-clear is atomic.
- Mode 2 formatter: `-(int32_t)v` safe for -32768, `tmp[5]` holds 5 digits, line max 22 B <= 24 B; ring room check before write.
- Mode 4 vs `main_record.c`: same init and loop, plus icon; `icon_show` accepts GESTURE_UNKNOWN (maps to the unknown icon); `show_frame()` result ignored on purpose (windows are seconds apart).
- HC-06 helper: U1BRG 416 -> 16e6/(4*417) = 9592 baud (-0.08 %), 34 -> 114286 (-0.79 %), both BRGH = 1; the TX ISR/ring is idle (U1TXIE = 0) during the polled phase so there is no conflict; the second AT string reaching a module already at 115200 is harmless; clearing OERR by writing 0 is the correct way and also flushes the RX FIFO. Waits are tick-based and bounded by Timer1 running.
- `config_bits.c`: COE removal is consistent with the v2.10 config doc; remaining pragmas unchanged. `models/gesture_model.h` forwards with a quoted include (resolved from its own directory); the synthetic header has include guards and its GM_* constants match `gesture_init(100, 4)`.
- Course rules: file-level and per-function `[AI-GENERATED]` markers present in main.c, ws2812_pic24.c/.h, ws2812_send.s (`;` form), gesture_model.h; AI_USAGE.md rows exist for every new function in main.c, ws2812_init/show/_ws2812_send_asm and gesture_model.h; fixed-width types, no float/malloc; every register write in the new code carries a bit-field comment; public ws2812 functions are documented in the header; `wait_ms` blocking delays live in app code, not library code.

## Open questions

1. Is `DISPLAY_CAP` 32 intentional for the whole matrix (F2)? If the MPLAB project overrides it with `-DDISPLAY_CAP=...`, F2's numbers change.
2. IPL write skid: the datasheet's rule for how many instruction cycles after a write to SR<IPL> an already-pending interrupt can still be taken was not re-read here. If it is more than zero, a Timer1 interrupt could land just before the first `bset` (not inside the bit loop, since IPL 7 is then in force), adding at most a long first low period (harmless). No change recommended unless the scope shows a first-pixel glitch.
3. Logic level: a 3.3 V PIC output driving a 5 V WS2812 data input is below 0.7 x Vdd; modes 1/3 work on the bench, so presumably the matrix runs from 3.3 V or tolerates it. Not a code issue, noted only because the C6.3 numbers assume it works.
4. Spec for mode 2 says "simulator only" in the owner's comment; the code is hardware UART + RB4 marker. Not a defect, but confirm that is what was meant.
