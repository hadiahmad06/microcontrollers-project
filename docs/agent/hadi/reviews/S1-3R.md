# S1-3R review: C4 / C5 quantization proposals

Reviewer: review-2 (did not write the work, wrote no code). Date 2026-11-14.
Reviewed (read-only, uncommitted in main checkout): `proposals/C4_model_header.md`, `proposals/C5_classifier_output.md`, `spikes/quant/quant_ref.py`.
Scratch tests (outside repo): requant corner and 2M-random re-check, modified demo, XC16 v2.10 compile/link tests.

## Verdict: REQUEST CHANGES (small, mostly exporter-recipe fixes; the core design is sound)

The requant math is correct and the split multiply equals the big-int definition on the stated domain. But the exporter recipe has a sign error that breaks the integer net on non-zero-mean data, the recipe and `mshift` can emit values outside the split's domain, C5's kNN-first rule can steal confident MLP results, and one shift expression is wrong on 16-bit `int`. All fixable in the docs; none changes the architecture.

### Checklist rulings
1. **Bit-exactness.** Fully specified: requant is applied to the *signed* acc; ReLU is the lower clamp 0 applied *after* the floor shift, so negative acc gives negative or 0, then 0 (`requant_big(-2^20,16384,16) = 0`). Floor semantics: Python `>>` and XC16 `asr` agree (DS-50002071M §23: "The sign is retained"; asm shows `asr`). `requant_split == requant_big`: proved analytically (nested floor: `floor((a*2^16 + c)/2^sh) = floor((a + floor(c/2^16))/2^(sh-16))`; |a| < 2^30; c < 2^31+2^30 < 2^32; sum fits int32) and tested: 960 corner combinations (acc at +-2^31 edges, +-65535/65536/65537, 0, +-1, +-2^30 x M in {2^14, 2^14+1, 2^15-1, 29100} x SH 16..31) and 2M random cases with int32/uint32 wraparound emulated: **no counterexample**. Domain violations come from the exporter (findings 2, 6), not the identity.
2. **16-bit overflow.** MAC `(int16)w*x` is safe only because |w*x| <= 16129 (int8 x int8, also layer 2); not for fallback (d) (finding 8). `(d2-d1)*255` is fine with the shown `(uint32)` cast (verified: without it XC16 emits a 16-bit `mul.ss` and truncates; with it `___udivsi3`). `margin >> GM_CONF_SHIFT` fine. `(1<<s)>>1` broken at s=15 (5). Split multiply untyped (6). `0x1A2B3C4Du` becomes `unsigned long`, fine.
3. **C3 interaction:** findings 7, 8.
5. **C5 logic:** findings 3, 4. IDs 9..12 are consistent with `int8_t gesture_classify` (max 12) and `gesture_learn(uint8_t)` range [9,12]. But the overview declares `void gesture_learn(...)` while C5 says it "rejects" bad ids: needs a status return (question 5). In step 2, the later `c < min_conf` check is redundant for the kNN branch but harmless.
7. **int8 x8 for kNN (PLAN 3.6 vs §4): sound.** PLAN l.113 already says "int8 normalized per the C5 proposal, pending Hadi", so only the old §3.6 wording conflicts. int8 L1 is arguably better than int16 L1 (raw int16 lets energy features up to 32767 swamp means). Caveats: distances depend on exporter OFF/SH (templates are RAM-only, so fine); coarse energy resolution (7) carries into kNN; fallback (d) breaks the budget unless kNN stays on int8. Accept; update PLAN wording.
6. **Course rules:** finding 12.

## Questions for Hadi
1. Treat findings 1-2 (offset sign, `mshift` domain) as blockers for the exporter ticket, with the demo made a real acceptance test?
2. Float training model: raw x with folded offset, or normalized x8 directly (my recommendation: x8 directly, no fold)?
3. Energy features: keep offset=mean plus max-based shift, or ask C3 for a compressed (sqrt/log) energy before the first training run?
4. kNN override policy (finding 3): who wins when the MLP is confident and a learned template is also within MAX_DIST?
5. `gesture_learn` is `void` in the overview but C5 says it rejects bad ids: add an `int8_t` status return?
6. Is the fallback threshold in finding 8 acceptable, and how large is the held-out set expected to be?
