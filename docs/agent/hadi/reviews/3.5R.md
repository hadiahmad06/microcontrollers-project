## 2. 16-bit int review

I read every expression with `int` = 16 bits.

- `knn_l1`: operands are widened to `int16_t`, the difference is at most 254, `uint16_t` sum at most 15300. No overflow.
- `recompute_radius`: `d[]` is `uint16_t`, 10 entries (20 B stack). `d[p - 1u]` is `unsigned int` arithmetic with `p >= 1`. `r` is `uint32_t`; the clamp is done in 32 bits before the `uint16_t` cast.
- `knn_query`: `best[]` sentinel 0xFFFF is above any real distance. `(uint32_t)(uint16_t)(d2 - d1) * 255u` is 32-bit (max 15300 * 255 = 3.9e6). Loop counters are `uint8_t`.
- `knn_import`/`knn_export`: `KNN_BLOB_SIZE` is 1214 and fits `unsigned int`. `4u + 2u * c` is computed in `unsigned int`. The running index `n` is `uint16_t`.
- `classify_mlp_conf`: shift on `uint32_t` by at most 24 in tests and 31 in principle; no shift of a 16-bit operand. Margin up to 2^30 tested.
- `classify_decide`: promotions of `uint8_t`/`uint16_t` compares are safe on a 16-bit target (`unsigned int`).

Result: no 16-bit bug. The sim16 build (avr-gcc, `int` is 16 bits) proves it: removing only the `uint32_t` cast makes the sim16 build fail while the host build still passes (mutation `no_u32_sim16_only`), so the second build earns its keep.
