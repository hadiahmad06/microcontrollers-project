## Findings

1. **HIGH, tools/recorder.py:243-255 (`_stdin_loop`, `poll_enter`, `announce_next` 326-331): stray Enter mislabels data.**
   The stdin thread queues every line. `poll_enter` drains the queue only while `waiting`. An extra Enter pressed during
   step k (double tap, or Enter to "confirm" a window) stays queued and is consumed instantly at the start of the
   wait for step k+1, so that wait ends with no user action and the next window is stored under the NEXT label while the
   user is still doing, or has not yet announced, the next gesture. Reproduced: queue two Enters, window 1 stored, window 2
   stored although the user never pressed Enter for step 2 (script in scratchpad `stray.py`; output
   `after w2 stored 2 waiting False`).
   Fix: when entering a wait (in `announce_next`, and `start_plan`), drain the queue (`while not q.empty(): q.get_nowait()`).
   Better: also discard Enters whose timestamp is older than the NEXT print. Add a test that injects two Enters.

2. **HIGH (usability), tools/recorder.py:465 (`rec.write()` after the loop; also 439-467 `run`): failed runs leave an empty
   OUT that blocks the retry.** Fatal exits 2 and 3 and zero-window runs all reach the final `rec.write()`. Reproduced:
   `--port /dev/nonexistent --out bp.npz` prints the error, creates an empty `bp.npz` (0 windows) and `bp.bin`, and the
   corrected command then fails with `bp.npz exists; use --append or another --out`. A mistyped macOS port name is the
   most likely first error. It also leaves an empty file that `--append` would later extend. Judgement of the deviation
   "OUT always written at the end": reject it.
   Fix: final write only if `rec.stored > 0` (or `--append`, where it just refreshes meta); never create OUT for exit 2/3
   with nothing stored. Likewise do not leave an empty raw log: create it lazily on first chunk.

3. **MEDIUM, tools/RECORDING.md:5-12 (macOS): no macOS guidance, examples are `/dev/ttyUSB0`.** On macOS the device is
   `/dev/cu.usbserial-XXXX` or `/dev/cu.usbmodemXXXX`; use `cu.*` (the `tty.*` twin can block on carrier detect and is
   for incoming calls). Say how to list (`ls /dev/cu.*`), that `pip install pyserial` is optional, that the first
   run may need the USB-serial driver (FTDI/CH340/CP210x) allowed in System Settings, and that only one program may hold
   the port. Also section 1 says the dry run "records nothing" but the command stores one window and creates the file;
   say `--label none --count 1` creates `/tmp/test.npz`, or use a different example.

4. **MEDIUM, tools/recorder.py:96-110, 442-467: a pyserial error ends in a traceback with no summary.**
   `serial.SerialException` (USB adapter unplugged mid-session, common) is not caught in `run`; the `except` clauses cover only
   KeyboardInterrupt and Fatal, so the summary/final write are skipped (the per-window file is still valid, which is why this
   is medium). Fix: catch `OSError` (SerialException derives from it) around the loop, print "serial device lost", and fall through
   to the summary with exit code 2.

5. **MEDIUM, tools/c2_proto.py:151-164 and recorder `summary` 366-367: junk "device text".** The deviation "garbage includes bytes
   rescanned after a CRC failure" is acceptable and consistent (the `--corrupt` test still equals the number corrupted
   because crc_errors counts candidates, not garbage), but those rescanned payload bytes also feed `text_lines`, so a corrupted
   frame can produce spurious "device text" lines (and `_line` is unbounded across a long printable run). Fix: cap `_line`
   at ~200 chars and, in `_scan`, mark the dropped-after-CRC bytes as non-text (e.g. clear `_line` and skip appending until the
   next 0x0A), or document it. Spec text says only bytes dropped while hunting count as text, which the rescan technically is,
   so this is a spec grey area; low impact on data.

6. **MEDIUM, tools/tests/test_recording.py (gap): the out-of-range rejection (recorder.py:284-286) has no test**; removing it
   fails 0 tests. It is also silent (counted in `rejected` only). Fix: test a window containing 2048 and -2049 is not stored and
   counts as rejected; print one stderr warning the first time (`window id N rejected: sample outside [-2048, 2047]`), since a
   wrong sensor range would otherwise look like a silent "nothing recorded".
   Judgement: rejecting out-of-range windows is correct (S4 validation would refuse the file anyway).

7. **LOW, tools/recorder.py:280-282: windows before the first HELLO count as `rejected`, no message.** Judgement: acceptable
   (spec only says not stored). The wand HELLOs every 2 s, so the first window after start can be lost with no hint. Fix: print
   once `waiting for HELLO (wand sends one every 2 s)` in non-quiet mode.

8. **LOW, tools/recorder.py:434-438 (raw log append and skip-if-equals-input): acceptable.** One trap: re-running with a deleted
   OUT but the same stem appends to the old `.bin`, so replaying that log mixes sessions. Fix: note in RECORDING.md ("delete the
   `.bin` too") or print the log path and its size at start when it is non-empty.

9. **LOW, tools/recorder.py:216-221: `--append` with an explicit `--session K` that already exists for the same subject is silent.**
   `merge` later refuses, but only if the files differ, and `train.py` would then group two sessions as one. Fix: warn when
   (subject, K) exists in the loaded file; same for default subject 0 / session 0 in two separate files (RECORDING.md mentions it,
   the tool does not).

10. **LOW, tools/recorder.py:339-355: per-window full rewrite plus fsync is O(N).** At 3000 windows about 2.7 MB per write; the
    macOS tty input queue is small (about 1 KB), so a write that outlasts a frame in flight could overrun. With one window per gesture
    (>=1 s apart) the risk is low; if gestures ever arrive faster, write every k windows or on step end, and always at exit.

11. **LOW, tools/recorder.py:119-147 (termios fallback on macOS): looks right** (`B115200` exists, raw cflag 8N1 CLOCAL, VMIN=0
    VTIME=0 with select, O_NONBLOCK, read of 0 bytes ends cleanly after unplug). Not verified on macOS hardware. Nits: no `TIOCEXCL`
    and no `tcflush(TCIFLUSH)` on open (stale bytes are tolerated by the decoder); `os.O_NONBLOCK` stays set on the fd, harmless.

12. **LOW, interactive Enter wait during a window (judgement of the deviation): behaviour is correct.** A window arriving while
    `waiting` is counted `skipped` and never stored; a step boundary starts waiting before the next window can be processed, so a
    window cannot be filed under the wrong plan step. Inherent hazard, document it: the last window of a step can be triggered by the
    hand returning, and the first window after Enter by a movement that started before Enter.

## Decoder judgement (S6/S7)
- False accept: needs known TYPE, exact LEN and a matching CRC-16; about 2^-16 per aligned candidate, inherent to the spec.
- Stall: a false WINDOW header swallows at most 922 buffered bytes (about 80 ms at 115200), then a CRC failure drops one byte
  and rescans the retained bytes, so no real frame is lost. `flush_stale` unsticks the tail only after >=50 ms idle and only
  in `--port` mode; `--input` replays never call it (a trailing false candidate at EOF is dropped silently, acceptable).
- Ctrl-C mid-write: `write_npz` unlinks its temp file and the old file stays; the window is already in memory and is included
  by the final write. Atomic write is correct (temp in same dir, fsync, `os.replace`).
- `train.py` loads the recorder output (checked) and `dataset_tool` accepts it.
